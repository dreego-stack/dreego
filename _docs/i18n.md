# Internationalization

Internationalization, commonly abbreviated to i18n because 18 letters occur
between the first and last letter, is a first-party Dreego capability. It is
available to every server-rendered page and component without repeating locale
setup in method sections.

## Configuration

Enable i18n in `dreego.config.json`:

```json
{
  "i18n": {
    "enabled": true,
    "defaultLocale": "de",
    "locales": ["de", "en"],
    "urlStrategy": "none",
    "detection": ["account", "cookie", "browser", "custom", "default"]
  }
}
```

Locales are canonical BCP 47 language tags. The default locale must appear in
`locales`. The `default` detector must be last. Core never performs IP
geolocation; an application or plugin can provide GeoIP as a custom resolver.
Optional `fallbacks` map a locale to an ordered list of other configured
locales. Dreego rejects unknown locales and fallback cycles during generation;
the website default remains the final fallback.

`urlStrategy: "none"` keeps routes such as `/account` unchanged when the user
switches language. Prefix and domain strategies are reserved for localized
public URLs.

With `urlStrategy: "prefix"`, `/en/account` selects English and routes
internally as `/account`. With `urlStrategy: "domain"`, configure every locale:

```json
{
  "domains": {
    "de": "example.de",
    "en": "example.com"
  }
}
```

Localized public content should usually use prefixes or domains for distinct
cache keys and indexable URLs. `none` is often preferable for authenticated
applications, but shared caches must respect the emitted `Vary` and
`Content-Language` headers.

The `lang` attribute on `<body lang="md">` or `<client lang="ts">` still names
the source processor. It does not select the visitor's locale.

## Catalogs

Place one or more JSON files below each configured locale:

```text
locales/
├── de/messages.json
└── en/messages.json
```

A basic catalog is a flat map of stable, namespaced keys:

```json
{
  "home.title": "Willkommen",
  "home.greeting": "Hallo, {name}!"
}
```

Plural and select values are structured so Dreego can validate every branch:

```json
{
  "cart.items": {
    "plural": {
      "argument": "count",
      "type": "cardinal",
      "cases": {
        "one": "Ein Artikel",
        "other": "{count} Artikel"
      }
    }
  },
  "account.salutation": {
    "select": {
      "argument": "form",
      "cases": {
        "formal": "Guten Tag, {name}",
        "other": "Hallo, {name}"
      }
    }
  }
}
```

Selectors can be nested. Every selector requires an `other` branch. Plurals
use Unicode CLDR cardinal or ordinal rules through `golang.org/x/text`.

Formatting metadata is explicit:

```json
{
  "invoice.total": {
    "text": "Gesamt: {amount}",
    "arguments": {
      "amount": {
        "format": "currency",
        "currencyArgument": "currency"
      },
      "currency": {}
    }
  }
}
```

Supported formats are string, number, integer, percent, currency, date, time,
and datetime. Date and time values are `time.Time`; a `timeZoneArgument` accepts
an explicit IANA time zone, and an optional per-locale Go `layout` controls the
rendered representation.

Currency formatting requires both the amount and an ISO 4217 currency code.
It only changes display conventions. Dreego never converts currencies, fetches
exchange rates, chooses a different currency, or owns financial rounding.

## Templates

Use message expressions in text positions:

```html
<body>
  <h1>[[ home.title ]]</h1>
  <p>[[ home.greeting name=user.Name ]]</p>
  <p>[[ cart.items count=len(items) ]]</p>
</body>
```

Message output is HTML-escaped. There is no raw translated HTML path. At
generation time Dreego rejects unknown keys, missing or unexpected arguments,
invalid catalogs, incompatible locale contracts, and missing default-locale
messages. Catalog files are compiled into generated Go and are not read from
disk in production.

The effective locale is available through `dreego.Locale(ctx)`. Full HTML
documents receive the matching `lang` attribute and right-to-left locales also
receive `dir="rtl"`.

`en-XA` and `ar-XB` are generated pseudolocales. They preserve placeholders
while exposing expansion and bidirectional-layout problems without requiring
translator-maintained catalogs.

## Resolution and replacement

Without localized URLs the standard order is account resolver, explicit locale
cookie, browser `Accept-Language`, ordered custom resolvers, then the website
default. Unsupported automatic hints are ignored. A user selection should be
persisted and followed by a local redirect to the original route.

`dreego.LocaleSelectionHandler` provides the optional POST-and-redirect flow.
It accepts a supported locale, stores an HTTP-only SameSite cookie, permits only
local return paths, prevents redirect loops, and works without JavaScript. Core
does not render a popup; a UI package such as `dreego-ui` can supply one.

The built-in catalog localizer belongs to `App`. Advanced applications can use
`SetLocalizer` before `Build` to replace it, or `DisableI18n` to disable it.
This keeps provider integrations and alternative catalog engines outside Core
without reducing the quality of the standard implementation.

## Translation tooling

Run `dreego i18n extract` to emit deterministic, versioned JSON containing the
default-locale messages, argument contracts, structured variants, and target
locale list. Translation-management adapters can consume this stream without
parsing `.dreego` files. Source catalogs remain the reviewable project truth;
production uses only their generated Go representation.
