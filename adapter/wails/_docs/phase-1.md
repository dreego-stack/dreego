# Wails v3 Phase 1

Wails v3 support remains experimental while upstream v3 is beta. Dreego's
adapter is intentionally smaller than a desktop framework integration: it
turns target-neutral Dreego pages and registered static assets into an
in-process `http.Handler` that Wails can use as its asset source.

The adapter never creates a Wails application, window, service, binding, or
lifecycle hook. It has no `Run` function and no Wails dependency. Application
code owns every Wails decision explicitly.

```go
dreegoApp := dreego.New()
if err := www.Register(dreegoApp); err != nil {
	log.Fatal(err)
}
handler, err := wailsadapter.New(dreegoApp)
if err != nil {
	log.Fatal(err)
}

wailsApp := application.New(application.Options{
	Name: "My App",
	Assets: application.AssetOptions{Handler: handler},
	Services: []application.Service{
		application.NewService(myService),
	},
})
wailsApp.Window.NewWithOptions(application.WebviewWindowOptions{
	Title: "My App",
	URL:   "/",
	Width: 800,
	Height: 600,
})
log.Fatal(wailsApp.Run())
```

## Route and asset boundary

Only pure pages registered through `App.RegisterRender` are available.
Generated pages without a `<server>` section receive that registration
automatically. Dynamic routes and SSR-only handlers are rejected because they
need request-specific state. Form actions, sessions, cookies, redirects, and
SSR middleware do not cross into the desktop adapter.

The handler accepts `GET` and `HEAD` for literal clean paths. Query strings,
encoded paths, traversal segments, backslashes, unknown routes, and other
methods are rejected. It starts no TCP listener. An application may still
create its own localhost server explicitly; that server is not owned or hidden
by Dreego.

## Wails toolchain

The reference application pins `github.com/wailsapp/wails/v3` to
`v3.0.0-beta.20`. The dependency belongs to the demo, not Core, SSR, the CLI,
or the adapter. Bindings are generated by Wails from application-owned
services. Dreego neither validates nor wraps those services.

All repository commands run through `smd`. Do not run `wails3 setup`
automatically because it may modify the host. The Phase 1 tests compile the
reference application, verify route and asset parity, exercise native history,
and inspect the complete native process tree for TCP listeners.

Restart-based development is the supported Phase 1 loop. Wails dev-server
behavior and broader lifecycle compatibility wait for upstream Wails v3
stability and Phase 2.
