# v0.8 stabilization

## Goal

Turn the multi-target v0.x work into a coherent production candidate. This
phase prioritizes compatibility, operations, security, accessibility, tooling,
and evidence from real applications over adding another target.

## Contract review

Review every exported identifier and generated contract across:

- root App and render APIs;
- SSR, SSG, and Wails targets;
- section and processor protocol;
- DreeJS manifests and network protocols;
- plugin registration and lifecycle;
- diagnostics, configuration, and CLI behavior.

Remove speculative exports before promising stability. Prefer additions over
changes after the review. Write migration guidance for every retained breaking
change made during v0.x.

## Reference applications

At minimum maintain:

- SSR SaaS slice with sessions, forms, protected routes, observability, and
  horizontal deployment guidance;
- SSG content or commerce slice deployed to GitHub Pages and Cloudflare Pages,
  including one optional dynamic component;
- Wails desktop slice using typed Go bindings without a local HTTP server;
- DreeJS live slice with reconnect, authorization, and multi-instance pub/sub;
- external Markdown and TypeScript processor examples.

## Quality gates

- Full behavioral, race, fuzz, security, and dependency suites pass.
- Benchmarks publish reproducible hardware and workload details.
- Client assets have size budgets per DreeJS module.
- Generated output is deterministic across supported platforms.
- Accessibility tests cover initial render and dynamic updates.
- Error messages are usable without color and include remediation.
- Supply-chain documentation covers managed tools and plugin executables.
- Upgrade, rollback, backup, and incident diagnostics are documented.

## Enterprise readiness evidence

Do not claim that targets alone make Dreego enterprise-ready. Publish evidence
for:

- server resource limits and graceful degradation;
- horizontal scaling and shared-session behavior;
- request, build, and client observability;
- security defaults and threat models;
- stable release and deprecation policy;
- plugin permission and provenance reporting;
- long-running compatibility tests;
- maintainer and security contact processes.

## v1 decision gate

v1 is a compatibility promise, not a feature dump. It is considered only after
real applications have exercised all contracts intended to become stable and
the project can maintain them. Unproven capabilities remain provisional or are
removed from the v1 promise.

## Not in this phase

- A new render target added to improve the feature list.
- SPA or Wasm unless a separate exploration has already proven clear value.
- Provider-specific infrastructure moved into core for convenience.
- Stability declarations based only on internal examples.
