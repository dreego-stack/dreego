# v0.8 module boundaries

## Objective

v0.8 is a deliberate breaking release that gives each independently consumed
Dreego capability its own Go module while preserving one repository, one
coordinated version number, module-store discovery, and repository-controlled
release automation. Wails is not shipped in v0.8. Its existing experimental
work is retained as input for a redesigned `adapter/wails` in v0.9.

## Modules and tags

| Directory | Module | v0.8 tag | Responsibility |
|---|---|---|---|
| `/` | `github.com/dreego-stack/dreego` | `v0.8.0` | Shared implementation under `internal/` and repository-wide metadata |
| `core/` | `github.com/dreego-stack/dreego/core` | `core/v0.8.0` | Public target-neutral application and render runtime |
| `adapter/ssr/` | `github.com/dreego-stack/dreego/adapter/ssr` | `adapter/ssr/v0.8.0` | Explicit `net/http` host and HTTP-only helpers |
| `dreegotest/` | `github.com/dreego-stack/dreego/dreegotest` | `dreegotest/v0.8.0` | Public application, render, generator, and CLI test helpers |
| `cmd/dreego/` | `github.com/dreego-stack/dreego/cmd/dreego` | `cmd/dreego/v0.8.0` | Installable CLI |

All v0.8 tags point to the same release commit. There is no
`adapter/wails/v0.8.0` tag. The first Wails adapter is planned for v0.9.

## Dependency direction

```text
cmd/dreego  ──> root internal
dreegotest  ──> root internal, core, adapter/ssr
adapter/ssr ──> core
core        ──> standard library and approved golang.org/x modules
root        ──> standard library and approved golang.org/x modules
```

`adapter/ssr` must not import `core/internal`. HTTP-only middleware and
validation currently reached through that boundary must move behind an
appropriate public contract or into `adapter/ssr` according to ownership.
No module may introduce a dependency cycle.

## Documentation ownership and discovery

Documentation remains stored beside source and is never embedded into the CLI.

- Repository-wide architecture, roadmap, and contribution material remains in
  `/_docs`.
- Core runtime documentation lives in `/core/_docs`.
- SSR hosting documentation lives in `/adapter/ssr/_docs`.
- Test-library documentation lives in `/dreegotest/_docs`.
- CLI, generation, and language-tooling documentation lives in
  `/cmd/dreego/_docs`.
- A future Wails adapter owns `/adapter/wails/_docs`.
- External plugins retain their own `_docs` and additional instructions.

Module and plugin locations are resolved through Go module metadata. Resolution
must support the current module, `go.work`, `replace`, vendor, and the module
cache without constructing cache paths manually. The installed CLI locates its
own module and root dependency through Go build information. Project modules
and plugins are resolved with `go list -m`. Repository-root discovery is kept
separate from module-root discovery.

## Local development

The repository owns a committed `go.work` that uses every local module. Local
development and CI therefore test local sources without committed `replace`
directives. Published `go.mod` files contain real versioned Dreego requirements.

All development commands continue to run through `smd`. Git operations remain
host-only. No build writes binaries outside `/tmp` or `./tmp`.

## Release behavior

The release workflow derives one version and updates only requirements whose
module path is `github.com/dreego-stack/dreego` or begins with that path plus
`/`. External requirements are never upgraded as part of a Dreego release.

Before tagging, CI must verify that:

1. every participating module uses the release version for internal Dreego
   requirements;
2. external direct requirements did not change unexpectedly;
3. each module passes its tests with workspace mode disabled and published
   versions available;
4. the complete repository passes through the local workspace;
5. every expected tag points to the same release commit; and
6. no unexpected module or tag participates in the release.

The release creates and pushes all participating tags as one guarded operation.
Partial tag publication is a failed release that requires repair before another
release begins.

## Migration surface

- `github.com/dreego-stack/dreego/core/ssr` becomes
  `github.com/dreego-stack/dreego/adapter/ssr`.
- `github.com/dreego-stack/dreego/cli/dreego` becomes
  `github.com/dreego-stack/dreego/cmd/dreego`.
- Core imports remain `github.com/dreego-stack/dreego/core`.
- Dreego test imports remain `github.com/dreego-stack/dreego/dreegotest`.
- Generated files use the new SSR adapter import.
- Old paths are removed without compatibility forwarding packages.

## Testing strategy

- Add structural tests for module paths, dependency direction, documentation
  ownership, and absence of old import paths.
- Test module discovery with workspace, replace, vendor, and module-cache
  fixtures.
- Test CLI installation and version selection with `cmd/dreego/v0.8.0` tag
  semantics in an isolated fixture.
- Run unit tests per module with workspace mode disabled.
- Run integration and race suites through the committed workspace.
- Validate release metadata and tag names without creating local release tags.

## Boundaries

### Always

- Keep the same version number across all modules participating in a release.
- Give every published module its own correctly prefixed tag.
- Keep docs and plugin instructions discoverable through Go module metadata.
- Preserve explicit `App` ownership and target-neutral rendering.

### Ask first

- Add another public module.
- Move a capability between public modules after this migration.
- Change which modules participate in a coordinated release.

### Never

- Embed documentation into the CLI.
- Add compatibility aliases for the removed import paths.
- Automatically upgrade external dependencies during a Dreego release.
- Publish Wails as part of v0.8.
- Treat the nearest `go.mod` as the repository root.

## Success criteria

- The five v0.8 module paths build and test independently.
- `go install github.com/dreego-stack/dreego/cmd/dreego@v0.8.0` resolves the
  `cmd/dreego/v0.8.0` module tag rather than the root tag.
- A consumer can use Core without downloading SSR or Wails dependencies.
- A consumer can add `adapter/ssr` explicitly and run an SSR application.
- `dreego docs`, module components, and plugin instructions resolve from local
  workspaces, replacements, vendor trees, and downloaded modules.
- The root module contains no Wails dependency or Wails implementation.
- CI can prepare all internal requirements and the complete tag set without
  changing external dependency versions.

## Deferred to v0.9

- `adapter/wails` public API and module.
- A Wails-owned application bootstrap using Dreego only as an in-process render
  and asset adapter.
- Wails-specific dependencies, bindings, native-window tests, and reference
  application.
