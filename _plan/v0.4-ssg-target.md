# v0.4 SSG target

## Goal

Build deployable static sites from the same target-neutral App and typed
components used by SSR. Static output must work on GitHub Pages, Cloudflare
Pages, object storage, and conventional static servers without a Go process.

## Target package

The intended package is:

```text
github.com/dreego-stack/dreego/target/ssg
```

The package owns route enumeration, output paths, document assembly, asset
writing, collision detection, and build reporting. It consumes the shared
renderer but does not import the SSR host.

## Static route model

Literal routes are enumerable automatically. Dynamic routes require typed
build-time parameters supplied by application code:

```go
type ProductParams struct {
    Slug string
}

func ProductPages(ctx dreego.BuildContext) ([]ProductParams, error) {
    return catalog.StaticProducts(ctx)
}
```

This is a contract sketch. The final API must preserve generated type safety,
deterministic ordering, cancellation, and clear ownership of external data.
SSG must not crawl a running application to infer its route set.

## Output rules

- `/` writes `dist/index.html`.
- `/about` writes `dist/about/index.html` by default.
- Route and asset collisions fail before partial output replaces a valid build.
- Builds write to a staging directory and publish atomically where practical.
- Asset names are content-addressed or otherwise deterministic.
- Base paths support repository-hosted GitHub Pages deployments.
- Canonical URLs and sitemap data are explicit rather than guessed.
- A build manifest records generated routes, assets, hashes, warnings, and
  processor versions.

## Dynamic components on static output

SSG determines initial HTML generation, not whether browser JavaScript exists.
A static page may include DreeJS local behavior, fetch, polling, streams, or
live connections when an external endpoint provides the required capability.

The build checks capabilities:

- local client behavior works without a server;
- fetch and polling require a configured reachable endpoint when they are not
  purely local;
- stream and live require an external server capability;
- server actions cannot be emitted as if the static host implemented them.

The initial HTML remains useful when optional client code fails unless the
component explicitly documents that it cannot degrade.

## Build-time data and security

Build processors may read approved files and environment variables through a
documented boundary. Secrets must not be serialized into HTML, manifests, or
client assets. Diagnostics should identify the source component and generated
route without echoing secret values.

Remote content loading needs timeouts, cancellation, bounded concurrency, and
deterministic caching behavior. A failed route fails the build unless an
explicit future partial-build mode defines safe semantics.

## Implementation slices

1. Render one literal route and write a complete document.
2. Emit multiple literal routes and shared assets deterministically.
3. Add typed enumeration for one dynamic route.
4. Add base-path, canonical URL, sitemap, and 404 behavior.
5. Prove GitHub Pages and Cloudflare Pages reference deployments.
6. Add DreeJS asset output after the DreeJS foundation exists.

## Acceptance criteria

- No HTTP server is started during build or preview rendering.
- Literal and typed dynamic routes generate deterministic output.
- Unsupported server capabilities fail at build time.
- Static HTML works without JavaScript for its documented baseline behavior.
- Assets are minimal, deduplicated, and referenced through portable paths.
- Reference deployments cover root-domain and sub-path hosting.
- Accessibility and output-safety checks run for every generated route.

## Not in this phase

- A CMS, content database, or Markdown implementation in the target package.
- Serverless functions disguised as static output.
- Cloudflare Workers or Wasm.
- Client-side routing or a full SPA navigation model.
