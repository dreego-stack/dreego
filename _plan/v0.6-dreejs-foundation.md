# v0.6 DreeJS foundation

## Goal

Add optional, generated browser behavior without turning every Dreego page into
a single-page application. Static HTML remains the default. Applications do
not receive a runtime unless their components request client behavior.

DreeJS is one product name and one compiler/runtime boundary. Terms such as
island, active component, and live component may be used comparatively in
explanations but are not separate Dreego subsystems.

## State boundary

Authoritative business state stays on the server or another explicit backend.
Client state is appropriate for presentation and predictable local behavior:

- countdown display;
- open or closed UI state;
- selected tab;
- local filtering of already available data;
- optimistic visual feedback that remains subject to server confirmation;
- animation and focus state.

Client state must not become authoritative for payment status, authorization,
inventory, account balances, order completion, or other security-sensitive
facts.

## Source model

The root client section is:

```html
<client lang="js">
    // Browser code
</client>
```

JavaScript is the dependency-free default. TypeScript and Lua are provided by
external language processors:

```html
<client lang="ts"></client>
<client lang="lua"></client>
```

Client code is scoped to a generated component instance contract. The compiler
must define props, element references, lifecycle, cleanup, and event binding.
Global script behavior remains an explicit escape hatch, not an accidental
side effect of every component instance.

## Component activation

Components retain the existing `<@Name>` identity. DreeJS behavior is expressed
through directives or compiler-detected client code, not a second component
sigil:

```html
<@Clock dree:client />
<@Stock dree:fetch="/stock/42" />
<@Stock dree:poll="1m" />
<@Notifications dree:stream="/notifications" />
<@Chat dree:live="/chat/general" />
```

These are semantic sketches. Exact directive values, typed endpoint contracts,
and error behavior require individual specs and integration tests.

## Runtime modules

```text
dreejs/
├── core/       component identity, lifecycle, DOM ownership, diagnostics
├── fetch/      one-time request and replacement
├── poll/       scheduled requests, visibility pause, cancellation, backoff
├── stream/     server-sent events and reconnection
└── live/       multiplexed bidirectional events and server-rendered updates
```

The source tree may use different private paths if the implementation remains
clear. Public contracts should describe capabilities, not filesystem layout.

Generation builds a client manifest from used components and directives. It
includes only required modules and component code. A page with no client
features produces no DreeJS asset.

## Initial scope

The foundation proves local client behavior before networked update modes:

- component instance discovery;
- typed serialized initial props;
- local event handlers;
- local presentation state;
- conditional display updates;
- lifecycle cleanup;
- deterministic asset generation;
- content security policy compatibility;
- accessible focus and announcement behavior.

A countdown is the reference slice. The server supplies an authoritative end
timestamp and renders both meaningful initial content and the states needed by
the component. The browser updates display time and switches to a prepared
finished view locally. Reloading reconstructs state from the authoritative
timestamp.

## DOM update model

Do not commit to a virtual DOM without evidence. Evaluate the smallest model
that preserves predictable component ownership:

1. generated direct DOM updates for known bindings;
2. template fragment replacement with focus preservation;
3. keyed morphing for server-produced HTML.

The first local-state implementation should prefer generated direct updates.
Network-produced HTML may later justify a small morphing layer. Every update
must preserve form values, selection, focus, accessibility announcements, and
user-owned DOM where its contract requires it.

## Serialization

Only explicitly generated client props cross the boundary. Serialization must:

- retain TypeScript declarations when the processor is installed;
- escape HTML and script contexts safely;
- reject unsupported types with a source diagnostic;
- avoid serializing secrets or full server objects accidentally;
- support stable identifiers without leaking pointer or process details;
- document time, numeric, optional, and error representations.

## Target compatibility

- SSR can emit initial HTML and DreeJS assets.
- SSG can emit the same assets; network modes require external endpoints.
- Wails can emit local code and use a host bridge where explicitly supported.
- Unsupported capability combinations fail during generation or build.

## Acceptance criteria

- A static component emits zero DreeJS bytes.
- The countdown reference works under SSR, SSG, and Wails where host behavior
  permits it.
- No application-owned npm configuration is required.
- Client code is scoped and cleaned up when its component is removed.
- Serialized values are typed, escaped, and minimized.
- Keyboard focus and screen-reader output remain correct after updates.
- CSP documentation covers generated and user-authored client code.
- Runtime failures are observable without exposing sensitive values.

## Not in this phase

- A client router or SPA navigation system.
- Automatic synchronization of arbitrary Go variables.
- Fetch, polling, SSE, or WebSocket implementation beyond interfaces needed to
  validate the local foundation.
- Go-to-JavaScript compilation.
- A framework-specific virtual DOM selected before measurement.
