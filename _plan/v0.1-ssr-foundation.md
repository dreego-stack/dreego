# v0.1 SSR foundation

## Goal

Ship a trustworthy SSR foundation before introducing target-neutral rendering.
v0.1 proves Dreego can generate, run, test, secure, and operate a normal Go web
application. It is a foundation, not a claim that Dreego will remain SSR-only.

## Product outcome

A developer can build a multi-page application with typed components, forms,
sessions, middleware, progressive enhancement, explicit application ownership,
and a production-configured HTTP server. Generated applications are plain Go
binaries and do not require a client runtime.

## Required contracts

- Every route, middleware, session store, static asset, and lifecycle resource
  belongs to an explicit `App`.
- Generated registration is explicit and returns errors.
- Components have typed named props and deterministic slot behavior.
- HTTP boundary strings remain explicit and are converted into typed domain
  values by application code.
- Security defaults cover request limits, timeouts, recovery, CSRF, output
  escaping, headers, and session policy.
- Diagnostics include path, line, column, severity, and actionable text without
  relying on color.
- Plugins register explicit behavior on an App and cannot weaken unrelated
  route defaults.

## Section migration gate

At the time this plan was written, the implementation still uses:

```html
<go></go>
<head></head>
<div></div>
<style></style>
<script></script>
```

The separate pre-v0.1 todo atomically migrates these names to `server`, `body`,
and `client`. The v0.1 release documentation and compatibility baseline must
describe only the post-migration names. The migration must not be partially
implemented across releases.

## Verification gate

- Full `make test` passes inside `smd`.
- Race tests pass for runtime and integration packages.
- Reference applications cover routes, forms, components, and one plugin.
- CLI generation and formatting are deterministic.
- No generated `dree.go` file is committed.
- Core and transpiler dependency checks pass.
- Public documentation describes only behavior present in the release.
- Release tags, main history, changelog, and change files agree.

## Architecture preparation

The SSR implementation should avoid unnecessary hard coupling between template
evaluation and `http.ResponseWriter`, but v0.1 must not introduce speculative
public render or target interfaces. Preparation is limited to clear ownership,
small internal boundaries, and tests that reveal HTTP assumptions.

## Not in this phase

- SSG, Wails, DreeJS, TypeScript, or language processors.
- Compatibility wrappers that preserve obsolete global state.
- A generic plugin lifecycle or capability interface without real consumers.
- Moving packages only to match a future directory sketch.

## Handoff to v0.2

Before v0.2 begins, capture a behavior inventory for SSR rendering: status,
headers, body, head assets, redirects, errors, request values, sessions, and
streaming. The render foundation must preserve the relevant behavior while
making non-HTTP rendering possible.
