# v0.2 render foundation

## Goal

Extract a target-neutral, typed rendering foundation from the proven SSR path.
The renderer produces document content and metadata without owning an HTTP
server, filesystem output, WebView, or client connection.

This phase may be a deliberate pre-v1 breaking change. It must end with one
coherent package model rather than compatibility wrappers around `core`.

## Intended package direction

```text
repo root
├── app.go                         public target-neutral facade
├── context.go                     shared minimal context capabilities
├── internal/
│   ├── app/
│   ├── render/
│   ├── compiler/
│   ├── assets/
│   └── validate/
└── target/
    └── ssr/
```

This is a responsibility map, not a mandatory file move. Before moving code,
inventory exported identifiers and generated imports. Prefer a root package
that applications import as `github.com/dreego-stack/dreego`. The SSR host is
selected explicitly through `github.com/dreego-stack/dreego/target/ssr`.

## Render contract

The renderer should accept a generated, typed page or component entry point.
It must not use `page string, data map[string]any` as the primary API.

A result needs enough structure for all first-party targets:

```go
type Result struct {
    HTML   []byte
    Head   []byte
    Assets []Asset
}
```

This example is intentionally incomplete. The implementation must decide:

- whether output streams directly to an `io.Writer`;
- how errors behave after partial output;
- how head and asset discovery works without double rendering;
- how target-required client metadata is represented;
- whether a complete document and a component fragment share one result type.

The decision is captured in an ADR before exporting the API.

## Context boundaries

Do not model non-HTTP rendering as a request with nil fields. Instead, generated
code depends on small explicit capabilities. Shared render inputs may include
locale, route parameters, build data, or request-local values. HTTP-only
operations remain in the SSR host.

The following must fail at generation or build time when unavailable:

- setting response headers in SSG;
- reading cookies in a pure build context;
- registering a server action for a target without server routes;
- requiring a persistent connection from an unsupported host.

Runtime panics caused by a nil request are not an acceptable capability model.

## App and host ownership

The target-neutral `App` owns route and component declarations, render
registration, shared assets, and validated configuration. It does not own an
HTTP server.

The SSR host owns:

- `net/http` integration;
- server timeouts and graceful shutdown;
- request and response adaptation;
- HTTP middleware execution;
- redirects, cookies, sessions, and streaming behavior;
- HTTP-specific health and readiness endpoints.

The same App may be passed to more than one host or builder when its declared
capabilities are compatible.

## Implementation slices

### Slice 1: behavioral inventory

- Add tests for the current renderer's observable SSR behavior.
- Classify every use of `*http.Request`, `http.ResponseWriter`, and
  `SSRContext` as render-neutral or HTTP-only.
- Record generated imports and public identifiers that will change.

### Slice 2: internal render result

- Introduce an internal typed result or writer contract.
- Preserve SSR output byte-for-byte where ordering is contractual.
- Keep the public API unchanged until the internal contract is proven.

### Slice 3: explicit SSR host

- Move HTTP ownership behind a target package.
- Generate registration against the target-neutral App.
- Prove redirects, sessions, middleware, errors, and shutdown behavior.

### Slice 4: public package migration

- Publish the root package and `target/ssr` API.
- Update generated imports atomically.
- Provide a migration guide from `/core`.
- Remove the obsolete public package instead of retaining indefinite wrappers.

### Slice 5: non-HTTP proof

- Render a page and component without `httptest.Server`.
- Verify head, styles, assets, escaping, errors, and typed props.
- Do not call this SSG or Wails yet; it is evidence for their foundations.

## Acceptance criteria

- The same generated component renderer is used by SSR and a non-HTTP test.
- Target-neutral rendering does not require an `*http.Request` or
  `http.ResponseWriter`.
- HTTP-only APIs are unavailable or diagnosed outside the SSR target.
- Primary render entry points remain typed.
- Applications explicitly import and start the SSR target.
- Core/transpiler dependency gates remain green.
- A migration document covers every changed public import and method.

## Risks

- Streaming and separate head collection can conflict. Decide whether streaming
  is an SSR-host feature layered over a render plan instead of promising both
  through one result type.
- A broad context interface recreates hidden HTTP coupling. Prefer narrow
  capabilities and generated compile-time checks.
- Moving all packages at once creates an unreviewable change. Land internal
  seams first, then perform the public migration in one bounded PR.
- Target names can leak into components. Capability requirements must remain
  the only supported conditional boundary.

## Not in this phase

- SSG file output, Wails APIs, DreeJS, or processor subprocesses.
- A universal `Target` interface.
- Dynamic render data maps as a replacement for generated props.
- Silent fallback when a target lacks a requested capability.
