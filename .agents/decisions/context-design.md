# Context Design (Interface + Target Structs)

**Date:** 2026-07-28
**Status:** Accepted
**Review:** GLM-5.2 Expert Review (.tmp/output1.md)

## Context

The `<go>` block in `.dreego` files needs a context for data access. Dreego supports three rendering targets:

1. **SSR** — `*http.Request` + `http.ResponseWriter`
2. **SSG** — Build time, no HTTP
3. **Wails v3** — WebView + In-memory IPC, no HTTP

## Problem

The `<go>` block is generated by the transpiler — the target is known at compile time. The developer should have a consistent API, but the targets differ fundamentally.

## Decision

**Slim interface for the common minimum + three concrete structs per target.**

```go
// Core interface — ONLY what all three targets need
type Context interface {
    context.Context                    // Deadline/Cancel Propagation
    Param(name string) string          // URL params / Frontmatter / Route params
    Data(key string) any               // Meta data from frontmatter / Build info
    Render(name string, data any) error // Nested rendering
}
```

```go
// Three concrete implementations
type SSRContext struct {
    R *http.Request
    W http.ResponseWriter
}
func (c *SSRContext) User() User { ... }          // ONLY SSR
func (c *SSRContext) Session() Session { ... }     // ONLY SSR
func (c *SSRContext) FormValue(k string) string { ... } // ONLY SSR
func (c *SSRContext) Redirect(url string) { ... }  // ONLY SSR

type SSGContext struct {
    Meta     Frontmatter
    OutputDir string
}
func (c *SSGContext) Frontmatter() Frontmatter { ... } // ONLY SSG

type WailsContext struct {
    App    *app.App
    Window *window.Window
}
func (c *WailsContext) SystemAPI() SystemAPI { ... } // ONLY Wails
```

## Why not the alternatives

| Option                    | Rejected because...                                     |
|---------------------------|------------------------------------------------------|
| B: Single struct with nil fields | Mixes concerns, runtime nil-crash risk            |
| C: Go's context.Context   | No API contract, type-assertion hell                |
| Generics                  | Only 3 fixed types, no n targets. Interface suffices   |

## Plugin Extension

Per plugin, a context wrapper with embedding + typed getter:

```go
// In plugin (dreego-auth)
type AuthPlugin struct { dreego.Plugin }
type AuthContext struct {
    dreego.Context
    user User
}

// Usage in <go> block
c := dreego.Get[AuthContext](ctx)
user := c.User()
```

No `c.Get("auth")` with `any` cast. No string key. Type-safe.

## Rationale

1. **Compile-Time Safety:** If developer calls `c.Session()` in SSG → compile error. No runtime panic.
2. **The codegen pass knows the target:** Generated code calls directly on the concrete type, not through the interface.
3. **The interface is documentation & test mock**, not a dispatch mechanism.
4. **Go-idiomatic:** Like `database/sql` — one interface, various driver implementations.

## Consequences

- Three codegen passes: SSR, SSG, Wails
- Each pass generates code against the concrete context type
- Target-specific methods only appear in their pass
- Interface usable for shared tests
- Plugins wrap via embedding, no central registry needed
