# Entscheidung: File-based Routing mit Chi

**Datum:** 23.07.2026
**Status:** Akzeptiert (erweitert durch [[routing-and-components]])

## Kontext

Moderne Frameworks (Next.js, SvelteKit, Nuxt) nutzen File-based Routing: Die Ordnerstruktur bestimmt die URL-Struktur.

Dreego soll das auch können — aber Go-idiomatisch.

## Entscheidung

**File-based Routing via Code-Generation, nicht via Laufzeit-Scanning.**

```
routes/
├── get.dreego           →  /
├── about.dreego           →  /about
└── users/
    └── [id].dreego        →  /users/:id
```

`dreego generate` scannt den `routes/`-Ordner und generiert eine `dreego_router.go`:

```go
// CODE GENERATED BY DREEGO. DO NOT EDIT.
func RegisterDreegoRoutes(mux *http.ServeMux) {
    mux.HandleFunc("/", RenderIndexPage)
    mux.HandleFunc("/about", RenderAboutPage)
    mux.HandleFunc("/users/{id}", RenderUsersPage)
}
```

## Begründung

1. **Maximale Performance:** Kein `filepath.WalkDir` zur Laufzeit
2. **Single Binary:** Kein Dateisystem-Zugriff nötig
3. **Compile-Time Safety:** Nicht existierende Routen brechen `go build` ab
4. **Typensicherheit:** Route-Parameter werden als typisierte Go-Variablen generiert

## Nested Layouts

```
routes/
├── layout.dreego          → Haupt-Wrapper (Navbar, Footer)
├── get.dreego           → Nutzt layout.dreego
└── admin/
    ├── layout.dreego      → Erweitert Haupt-Layout um Admin-Sidebar
    └── settings.dreego    → Nutzt admin/layout.dreego
```

Layouts werden automatisch kaskadiert (wie in SvelteKit).

## Konsequenzen

- `dreego generate` muss den `routes/`-Ordner parsen
- Layout-Dateien (`layout.dreego`) werden speziell behandelt
- Dynamische Segmente: `[param]` → `{param}`, `[...catchall]` → `{catchall}`
- Die generierte Router-Datei wird nicht committed
